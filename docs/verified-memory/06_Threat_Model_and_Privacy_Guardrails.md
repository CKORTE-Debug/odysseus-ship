# 06 - Threat Model and Privacy Guardrails

## Purpose
Verified Memory is a trust-sensitive feature. The most serious bugs are not crashes; they are privacy leaks and false trust.

This document defines what can go wrong and the hard guardrails Codex must preserve.

## Core security principle

> The LLM may propose. Deterministic policy code decides.

The LLM must not be the final authority for privacy, staleness, source ranking, or overwrite decisions.

## Main threat categories

### 1. Private data leaked to web search
Risk: A user’s local/client document contains a company name, employee name, email, ticket ID, IP address, hostname, or internal filename. The model generates a search query containing that private data.

Guardrail:
- Every web query from Verified Memory must pass through `query_sanitizer`.
- The sanitizer must be deterministic.
- Block or sanitize before calling existing Odysseus search.
- If uncertain, block and require user approval.

### 2. Stale memory treated as current
Risk: A memory from months ago is reused as if it were fresh.

Guardrail:
- Every `MemoryClaim` must have `created_at`, `last_verified_at`, and `stale_after_days` or a `never stale` rule.
- Stale claims may be used as leads, not confirmed facts.
- Final answer context must label stale and unverified claims.

### 3. Unsupported AI summary stored as fact
Risk: The LLM summarizes a source badly, and the summary becomes memory without preserving the original evidence.

Guardrail:
- Store original `DocumentChunk` / `SourceRef` with line/page/chunk references.
- Summaries cannot replace original evidence.
- Claims generated by LLM must start as `unverified` or `candidate_update` unless source evidence supports them.

### 4. Wrong citation attached to answer
Risk: The answer cites a source reference that does not actually support the claim.

Guardrail:
- The final answer may only cite source refs included in the context package.
- Citation integrity tests must check that answers cannot invent source IDs.
- Evidence checking should compare claim text and cited chunk text before marking verified.

### 5. Low-quality source overwrites high-quality source
Risk: A forum, Reddit post, or SEO blog contradicts official documentation and overwrites the official memory.

Guardrail:
- Source ranker must classify source quality.
- Low-ranking sources can create notes or leads but cannot overwrite official-source claims automatically.
- Updates must create candidate records, not overwrite memory.

### 6. Legacy memory confusion
Risk: Legacy `memory.json` entries are mixed with verified memory and treated as sourced/verified.

Guardrail:
- Keep Verified Memory separate from legacy memory in early phases.
- Imported legacy memory, if ever supported, must be marked `unverified` with low confidence.

### 7. External API model leakage
Risk: Private local documents are sent to external model APIs.

Guardrail:
- Private Mode must avoid external model calls.
- The system should label context sensitivity before deciding whether an API model may be used.
- This project does not need to solve complete model-provider privacy in Phase 1, but it must not make leakage worse.

### 8. Automatic refresh causes memory poisoning
Risk: Nightly refresh uses bad sources or bad queries and corrupts stored memory.

Guardrail:
- Nightly refresh is out of scope until manual refresh is safe.
- Refresh creates `VerificationRun` and candidate update records.
- No silent overwrite.

## Query sanitizer hard rules
Block queries containing:

- Email addresses
- Phone numbers
- IPv4 or IPv6 addresses
- Internal domains
- Hostnames that look internal
- Ticket IDs such as `INC12345`, `REQ12345`, `CHG12345`
- Client names from denylist
- Person names from denylist
- Local file paths
- Private filenames marked internal
- Contract numbers or project codenames

Allowed terms include vendor/application names such as:

- Microsoft
- Windows
- Intune
- Entra
- Teams
- SharePoint
- Surface
- Apple
- Google
- Adobe
- Cisco
- Fortinet

## Safe query transformation examples

### Example 1
Bad:

```text
ClientName John Smith Teams hidden folder direct link
```

Good:

```text
Microsoft Teams folder visible by direct link not shown in Files tab SharePoint permissions
```

### Example 2
Bad:

```text
192.168.10.22 Intune enrollment error client.local
```

Result:

```text
blocked_by_privacy
```

### Example 3
Allowed:

```text
Microsoft Intune Autopilot OOBE Wi-Fi driver missing
```

## Memory overwrite rules
- Existing verified claims must not be overwritten automatically.
- New evidence creates a candidate update.
- Contradictions create `ConflictRecord`.
- A user or explicit approved workflow resolves the conflict.

## Audit logging requirements
Every verification action should record:

- memory claim ID
- original query
- sanitized query or block reason
- source rankings
- result
- timestamp
- whether memory was changed

## Required tests
Codex must add or maintain tests for:

- private query blocking
- allowed vendor query passing
- stale memory detection
- source ranking
- no automatic overwrite
- conflict record creation
- citation/source reference integrity

## Red flags during code review
Reject code that:

- Calls search before query sanitizer.
- Uses LLM judgment as the only privacy check.
- Stores generated memory without timestamps.
- Treats missing `last_verified_at` as fresh.
- Overwrites verified memory during refresh.
- Mixes legacy `memory.json` into verified memory without marking it unverified.
